# Signed state updates from your laptop

The owner requested updates without rebuilding the app on 2026-09-30. This extends WP-303/WP-501 and REQ-CAT-002, REQ-CAT-006, REQ-CAT-007, REQ-CFG-002, REQ-USR-002, REQ-SEC-001, REQ-UX-001 and REQ-A11Y-001. It uses a separate, explicitly approved laptop signer for the **Open Outdoor Local** app (`org.openoutdoor.local`), under ADR-052. Production release trust remains governed by ADR-031 and the [external signing-key procedure](CATALOG_SIGNING_KEY_PROCEDURE.md).

## Use it

1. Install the app build containing this feature once. Compatible later state snapshots do not need another app build.
2. Rebuild or restore the desired public state packages on the laptop using [package maintenance](PACKAGE_MAINTENANCE.md). Keep the generated `loader-inventory.json` with its exact SQLite files. Restart `pnpm map:laptop` after changing them: the server publishes a verified startup snapshot.
3. Open the printed `/pair` link on the laptop. In the phone's **Connect to laptop** panel, scan its QR code. For manual pairing, copy the address, session code and full **signing fingerprint** from that page or terminal.
4. Choose **Trust updates** after verifying that the pairing page belongs to your laptop. A public key received from the network alone cannot enable this approval. QR pairing only carries the independent fingerprint; approving trust is a separate explicit action.
5. Review **Installed snapshot**, **Available snapshot**, packaging dates, version and sizes. Choose **Update** for an installed state or **Download** for a new state. **Check for updates** refreshes the connected server's published list.

Packaging dates describe when the package was built, not a guarantee that every upstream record is current. Rebuilding sources remains a laptop operation. Downloads are selected individually; there is no background sync or source acquisition on the phone. Original build-pinned files can still be installed without approving update trust. The new client also accepts the older server's build-pinned catalog; an older app needs the updated build to read the new signed-server catalog or its version-two QR code. Files imports remain available for matching build pins.

## Signing and trust

The laptop creates its own Ed25519 key at `%LOCALAPPDATA%\OpenOutdoor\laptop-signing\identity.json` on Windows, or `~/.local/share/OpenOutdoor/laptop-signing/identity.json` elsewhere. It is outside Git and the served public-package root. Windows disables inherited directory access and grants the current account, SYSTEM and administrators; Unix uses a private directory and file modes. The key is never sent to the phone, printed, committed, uploaded to CI or included in package mirrors. Protect this directory separately if you need to preserve the signing identity across a laptop replacement. Loss or replacement changes its fingerprint and requires new phone approval. Do not move production release keys into this directory.

The public fingerprint is SHA-256 of the raw 32-byte Ed25519 public key. The authenticated package catalog supplies only the public key; the phone compares its fingerprint to the independently scanned or manually entered value before approval. Bonjour never advertises the fingerprint or any credential. The laptop-only QR page displays it for comparison. The fingerprint is a persistent signing identity, not a machine/account name.

Each signed manifest binds the public classification, state, name, SQLite and tile hashes, transfer/installed sizes, packaging date, package schema, supported app-major interval and monotonic revision. The existing WP-010 envelope format binds its exact manifest bytes, `public` data channel and the separate `paired-laptop-v1` trust root. Raw manifest bytes are transported as base64 to avoid cross-language reserialization. Apple [CryptoKit](https://developer.apple.com/documentation/cryptokit/curve25519/signing/publickey) verifies Ed25519 on the phone. The current reader supports SQLite package schema 1/app major 1; an incompatible engine/schema still requires a new app build.

Revisions are allocated durably before publication, starting from the laptop clock and increasing for changed snapshot metadata. Unchanged snapshots retain their revision/digest across restarts. A writer lock prevents two server processes sharing one signing identity; a dead process's lock is recovered, while unreadable/ambiguous locks fail closed. Corrupt identities/counters also fail closed rather than silently creating a new key. Correct the laptop clock or recover its identity if a publication revision is behind the phone's accepted floor.

Phone enrollment and accepted per-state revision/digest/date floors live in a device-only [Keychain item](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly). There are at most eight remembered signing identities and fifty state floors. Removing a package, disconnecting, explicit rollback and revoking/reapproving a laptop do not clear replay history. Trust does not migrate through the ordinary app-container backup. Keychain persistence failure leaves authorization unchanged; the native queue serializes trust and activation operations.

## Failure, rollback and revocation

The phone rejects tampered signatures/manifests, mismatched QR fingerprints, unapproved/revoked keys, private classification, incompatible schema/app intervals, older revisions, conflicting bytes at an accepted revision and older packaging dates. Invalid signatures abort the list; stale verified publications are withheld and counted as blocked. Exact retries/reinstallation of the latest accepted snapshot are allowed, including after rollback. Signed metadata must match the SQLite's embedded state/classification/schema/tile digest and packaging date. File length, hashes, SQLite integrity, embedded tile extraction, storage ceiling/reserve and atomic activation checks remain in force.

The highest accepted version is recorded only after file/tile validation and before atomic pointer publication. The protected active/backup registries allow at most fifty entries and 1 MiB each, covering current/previous signed proofs. Oversized publication is rejected before changing either pointer. If pointer publication is interrupted, the previous active state remains usable and the exact candidate can be retried. Rollback swaps the existing verified current/previous snapshots without lowering the replay floor. It cannot authorize an older network download. Files imports retain their compiled allowlist and cannot overwrite a state with previously accepted signed updates; use the signed connection or explicit rollback instead.

**Revoke trust** blocks future installations from the connected signer. Expand **Trusted laptops** to revoke a saved key while completely offline. Revocation retains public-key history so previously verified installed maps and rollback versions remain readable. A lost or compromised laptop can be revoked without contacting it. Reapproval requires its independent fingerprint again and retains replay floors. Disconnecting only clears the session credential, not persistent update trust.

Downloads remain local HTTP on trusted Wi-Fi. Signatures protect authorization/integrity, not transport confidentiality. Notes, recordings, private imports, public/private storage separation and existing rollback/reserve rules are unaffected. No database migration or production-release acceptance is claimed.

## Verification

`pnpm test:laptop` covers signing, durable counters, writer exclusion, signed-server responses, QR fingerprints, manual fallback, approval failure, update controls, stale refresh, revocation and retained user/package state. `pnpm quality`, privacy checks, documentation checks and the iOS bundle validate the integration.

The macOS iOS workflow additionally generates ephemeral synthetic Node signatures and runs the actual Swift CryptoKit trust class against them using in-memory Keychain persistence. Cases cover independent Node/Swift digest/signature agreement, unenrolled/wrong-fingerprint keys, failed saves, per-state/persistent replay floors, conflicting/old/incompatible publications, revocation/reapproval, explicit rollback authorization and exact retry. No private key is emitted in the vectors or artifacts. Native compilation and physical acceptance remain distinct.

Required iPhone cases: initial approval and wrong fingerprint; new public snapshot installed without rebuilding the app; cold restart and offline use; latest retry after explicit rollback; removal/reinstall without replay-floor reset; key loss/rotation and offline revocation; denied/locked Keychain access; interrupted pointer publication; large update/low space; tampered/older/incompatible files; unchanged notes/recordings and private overlays. These physical results remain pending.
